03

Eu

Compilo e reinicio o staging

Dois comandos. O precompile reconstrói o front; o restart troca o que está no ar.

cd /home/chatwoot/chatwoot
RAILS_ENV=production NODE_OPTIONS='--max-old-space-size=8192' \
  bundle exec rake assets:precompile > build.log 2>&1; echo $?
sudo /bin/systemctl restart chatwoot.target

O build leva de 6 a 10 minutos e é seguro de rodar com o app no ar — a troca só acontece no restart. Depois do restart o domínio devolve 502 por 30 a 40 segundos; não é falha, é o boot.

Armadilha

Nunca canalizar o precompile para | tail ou | grep: o código de saída passa a ser o do tail, e um build quebrado chega como sucesso. Já custou um "corrigi e deployei" falso, com o restart rodando sobre assets velhos.

E 4096 de heap agora dá OOM — o bundle cresceu. É 8192.

05

Eu

Fecho o commit na branch nicolas

Mensagem em Conventional Commits — fix(kanban): ... — porque o título do PR lá na frente é gerado a partir dela.

Armadilha · ordem importa

Commit antes do próximo restart. O app_version.rb carimba o SHA no boot e escreve o version.json; o front só manda o navegador recarregar quando esse valor muda. Restartar antes de commitar carimba o SHA velho — o usuário continua vendo o bug com o bundle antigo em cache, e parece que a correção não funcionou.

Muro — daqui a frota não é alcançável

O host nicolas é pull-only: não tem a chave simplex.linux.pem, não tem sshpass, não tem rota de ssh para o .229 e nem aparece na lista de VMs do deploy.sh. Tudo abaixo desta linha passa obrigatoriamente pelo GitHub.

06

Eu

Levo só o seu fix para um PR

A producao não está atrás da nicolas — elas divergem. A producao recebe PR de outras pessoas o tempo todo (em agosto eram 236 commits só dela contra 84 só da nicolas). Um PR de branch inteira nasce conflitando em centenas de arquivos. O caminho que funciona é isolar a sua correção:

git fetch origin producao
git worktree add -b spx/<fix> /tmp/<dir> origin/producao
ln -sfn /home/chatwoot/chatwoot/.husky/_ /tmp/<dir>/.husky/_   # antes do cherry-pick
git -C /tmp/<dir> cherry-pick <sha>
git -C /tmp/<dir> push -u origin spx/<fix>
gh pr create --base producao --title "fix(escopo): ..."

O origin busca por SSH com a deploy key e empurra por HTTPS com o token do gh — os dois lados de propósito, porque a deploy key é só de leitura.

Armadilha

O symlink do husky vem logo depois do worktree add: o .husky/_ é gerado pelo pnpm install e não vai no git, então em worktree o hook morre. Se você deixar para depois, o cherry-pick --continue quebra no meio da resolução de conflito.

07

Você

Você mergeia o PR

O gh pr merge é bloqueado para mim no modo automático — quem clica é você. Duas coisas para não se assustar e não se enganar:

O CI vermelho quase nunca é seu

O repo inteiro tem 762 problemas de eslint, então lint-frontend, frontend-tests, as 16 fatias de backend-tests e o Check Deployment falham em qualquer PR, inclusive nos que já foram mergeados. O único check que barra de verdade é o Validate PR title: o título precisa ser Conventional Commits. Título em prosa reprova em 5 segundos e se conserta com gh pr edit <n> --title.

Selo de "merged" não prova nada

Em 29/08 o PR #73 apareceu MERGED e o código não entrou: a producao foi reescrita depois e o commit de integração ficou órfão. A conferência real é git merge-base --is-ancestor <sha> origin/producao — eu rodo isso e te confirmo antes de qualquer um pedir o deploy.

Quem tem acesso ao 192.168.8.229

Deploy da frota

Um comando no orquestrador, que percorre as VMs uma a uma:

./deployment/deploy.sh producao

Por VM: git pull → bundle install → pnpm install → assets:precompile → db:migrate → restart chatwoot.target. Nas máquinas remotas isso vai encapsulado no cwctl -U producao. VM que já está no último commit é pulada.

Antes de rodar

Backup do banco. As migrations são idempotentes, mas o db:migrate roda em produção de cliente real — é o único passo do fluxo que não tem volta fácil.

09

Depois do deploy

Ligar a feature e conferir

Correção de bug já vale assim que a VM reinicia. Feature nova entra desligada e se habilita conta por conta — piloto primeiro, nunca a frota inteira de uma vez.

Risco nº 1 — bit de flag reclamado

O feature_flags é um bitmask bigint de 63 bits e está cheio, então flags novos reaproveitaram bits de flags antigos: response_bot→message_sequences, message_reply_to→internal_chat, report_v4→ai_assistant_v2, mobile_v2→report_rollup. Se alguma conta de produção tiver o flag velho ligado, o novo liga sozinho no deploy.

Por isso a pré-checagem roda antes do pull, ainda com o código antigo — depois não dá mais para saber qual dos dois o bit significava.

Fecha com o smoke: abrir o chat de um cliente, mandar e receber uma mensagem, conferir que o Sidekiq subiu com os crons novos.
