## 1. Tarefa 1 — `Conversations::OrphanRetriageJob` (issue 68)

### 1.1 O que mudou

**`app/jobs/conversations/orphan_retriage_job.rb`**

| Linha | Mudança |
|---|---|
| `:10-20` | `perform` passou a iterar com `rescue StandardError` **por conversa**: log + `ChatwootExceptionTracker`, e segue para a próxima |
| `:31-37` | query extraída para `#orphan_scope`, agora com **`.where.not(contact_id: nil)`** |
| `:52-57` | ordem invertida — `mark_alerted` **antes** de `notify_admins` |
| `:60-63` | `#mark_alerted` extraído (era o `update!` inline da antiga `:37`) |

**(a) Guard `.where.not(contact_id: nil)`** — confirmei o precedente citado no G1: `app/jobs/conversations/resolution_job.rb:28-29` faz exatamente isso, com o comentário *"Exclude orphan conversations where contact was deleted but conversation cleanup is pending"*. O `OrphanRetriageJob` é o job irmão e não herdou o guard. Segui o mesmo padrão e nomeei a razão no comentário.

**(b) Blindagem do laço** — a correção que importa a médio prazo. O guard resolve *este* dado ruim; o `rescue` por item resolve a *classe* do bug: nenhuma conversa individual pode mais interromper as outras 99 do batch. É o mesmo padrão que `#retriage` já usava internamente (`:82-84`).

**(c) Ordem notify × marcador** — era a origem do spam de 20 dias para os admins. `notify_admins` rodava, `update!` explodia, o dedupe nunca existia, e o ciclo repetia a cada 5 min. Agora o marcador é gravado primeiro; **se ele não puder ser gravado, o alerta não sai**.

> Trade-off explícito, para o coordenador validar: essa ordem troca "spam infinito" por "um alerta possivelmente perdido" no caso raro em que a conversa é órfã legítima *e* o `update!` falha por outro motivo. Considero a troca claramente favorável — o alerta perdido fica registrado no log e no GlitchTip com `conversation=<id>`, enquanto o spam não tinha fim nem diagnóstico. Se preferir o contrário (notificar sempre, mesmo sem dedupe), é uma inversão de duas linhas.

### 1.2 O que **não** fiz (fora do escopo, decisão do coordenador)

- **Limpeza dos dados órfãos na Tozi PROD** (opção b1 do G1: `Internal::RemoveOrphanConversationsService.new(account: ..., days: 3650).perform`). É escrita destrutiva em PROD de cliente, com `destroy_all` cascateando mensagens/SLAs/reporting_events. **Não executei** — a task proíbe e o G1 já a classifica como higiene não urgente. Com o guard no lugar, o sangramento para sem tocar em dado.
- **Migration de `NOT NULL` em `conversations.contact_id`** — a raiz estrutural (schema nullable × model `presence: true`). Fora de escopo, exige limpeza prévia.

## 2. Tarefa 2 — Captain `EpisodeSegmenterService` (issue 128)

### 2.1 Por que a conversa vem nil — **confirmado**

Reli o diagnóstico e reconfiri as três evidências no código atual:

1. **Sem FK.** `db/schema.rb:439-457` cria `captain_conversation_episodes` com `conversation_id bigint NOT NULL` e nenhuma `add_foreign_key` para a tabela; a migration de origem `db/migrate/20260717120000_...` também não a cria.
2. **Sem `dependent:` no lado da Conversation.** `enterprise/app/models/captain/conversation_episode.rb:10` declara só o lado filho (`belongs_to :conversation`), que valida na escrita e não protege contra deleção posterior. Não há `has_many :captain_conversation_episodes` em `Conversation`.
3. **Conversas somem por caminhos assíncronos** (`DeleteObjectJob`, `destroy_async` de contato/inbox/conta).

Resultado: episódio sobrevive à conversa. `pattr_initialize [:conversation!]` exige a **chave**, não rejeita `nil` — o `nil` chega intacto até `#rows`.

### 2.2 O que mudou

**`enterprise/lib/captain/episode_segmenter_service.rb:21-27`** — guard no ponto onde o nil aparece:
```ruby
return [] if conversation.nil?
```
`[]` e não `nil` porque `#perform` contratualmente devolve a lista de registros de `#persist`.

**`enterprise/app/jobs/captain/conversation_eval_scheduler_job.rb`**

| Linha | Mudança |
|---|---|
| `:19-33` | `perform` com `rescue` **por conta** — uma conta com dado inconsistente não impede o eval das contas seguintes do `find_each` (era o dano mais grave: contas com id maior nunca processavam) |
| `:37-40` | helper `#report` (log + `ChatwootExceptionTracker` com a conta no contexto) |
| `:69-80` | `segment_touched_conversations` com `rescue` **por conversa** |
| `:88-102` | `resegment_stale_open_episodes`: `.includes(:conversation)` → **`.joins(:conversation).preload(:conversation)`** + `rescue` **por episódio**. Também qualifiquei `captain_conversation_episodes.last_message_at` no `where`, porque o `joins` traz `conversations` para o mesmo escopo |

O `joins` elimina o órfão no SQL (INNER JOIN), o `preload` mantém o comportamento sem N+1 que o `includes` dava, e o `rescue` cobre o que o SQL não pega. Defesa em profundidade proposital: na mutação em que reverti o `joins`, o job continuou não explodindo — só passou a *reportar* o órfão em vez de pulá-lo.

### 2.3 (c) O episódio órfão: ignorar, marcar ou remover? — **decisão argumentada**

**Recomendo IGNORAR em runtime e REMOVER numa migration dedicada, com FK.** Nenhuma escrita foi executada.

| Opção | Avaliação |
|---|---|
| **Ignorar** (implementado) | ✅ **É o correto para o runtime.** Um episódio sem conversa não tem mensagens para segmentar nem para julgar — é irrecuperável pela mesma lógica da conversa sem contato: não há o que avaliar. Custo zero, reversível, sem escrita. |
| **Marcar** (ex. flag `orphaned_at`) | ❌ **Descarto.** Exigiria migration de coluna para criar estado que nenhum consumidor lê. O `boundary_reason` é validado por `inclusion:` numa lista fechada, então nem daria para reaproveitá-lo sem alterar o model. Adiciona complexidade sem nenhum ganho operacional. |
| **Remover** | ⚠️ **Certo como higiene, errado dentro do scheduler.** Um job de agendamento que apaga registros do cliente em silêncio é uma escrita destrutiva escondida atrás de um cron — a mesma classe de decisão que produziu este bug. O lugar da remoção é uma migration explícita, revisável e com janela. |

**Proposta para o coordenador decidir — NÃO EXECUTADA (camada 3 do G2):**

```ruby
# Migration dedicada. Ordem obrigatória: a FK FALHA se sobrar um órfão.
# 1) contar antes (SELECT):
#    SELECT count(*) FROM captain_conversation_episodes e
#     WHERE NOT EXISTS (SELECT 1 FROM conversations c WHERE c.id = e.conversation_id);
# 2) limpar:
#    DELETE FROM captain_conversation_episodes e
#     WHERE NOT EXISTS (SELECT 1 FROM conversations c WHERE c.id = e.conversation_id);
# 3) blindar:
add_foreign_key :captain_conversation_episodes, :conversations, on_delete: :cascade
# 4) e no model Conversation:
has_many :captain_conversation_episodes, class_name: 'Captain::ConversationEpisode', dependent: :delete_all
```

⚠️ Antes de rodar isso na Tozi, verificar `captain_conversation_evals.episode_id`: o eval aponta para o episódio (`belongs_to :episode, optional: true`) e essa tabela **também** não tem FK. Um `DELETE` de episódios órfãos deixa `episode_id` dangling nos evals correspondentes. Ou se limpa/nulifica junto, ou a FK dos evals precisa entrar na mesma migration. **Isso não estava no G2 e é a razão pela qual eu não trataria essa migration como trivial.**

## 4. Riscos e o que ficou de fora

### Riscos das mudanças

| Risco | Avaliação |
|---|---|
| O guard `contact_id` deixa de processar conversas que hoje "seriam" processadas | **Nenhum na prática** — hoje elas só produzem exceção. O guard restringe um escopo de **leitura**. |
| `includes` → `joins` muda a semântica da query | Muda de propósito: LEFT OUTER → INNER JOIN. O único registro excluído é o órfão, que já era fatal. `preload` preserva o carregamento em 1 query extra. |
| Alerta de órfã perdido se o marcador não gravar | Aceito conscientemente (§1.1c). Fica no log e no GlitchTip com o id da conversa. |
| Os `rescue` mascararem bugs novos | Mitigado: **todo** `rescue` loga com contexto (`account=`, `conversation=`, `episode=`) **e** reporta ao GlitchTip. O volume cai de "1 evento a cada 5 min para sempre" para "1 evento por item problemático por execução" — sinal, não sangramento. |
| Interação com o WIP de outros workers | Toquei apenas os 3 arquivos de app + 3 de spec sob minha propriedade. `git diff --stat` mostra o resto do working tree intacto. |

### Fora de escopo (deliberadamente não feito)

1. **Nenhum commit** — working tree, conforme instruído.
2. **Limpeza de dados na Tozi PROD** (conversas sem contato; episódios órfãos) — descrita acima, decisão do coordenador.
3. **Migration de FK/`dependent:`** para `captain_conversation_episodes` — proposta em §2.3, com o alerta sobre `captain_conversation_evals.episode_id` que **não** consta do G2.
4. **`NOT NULL` em `conversations.contact_id`** — raiz estrutural apontada pelo G1 §7.
5. **As 12 ofensas de RuboCop preexistentes** no segmenter — exigiriam refatorar `build_segments`/`persist`, fora do escopo.
6. **Issues 65, 86, 160 do G2** — não são desta task (a 65 aparece no `git diff` como WIP de outro worker em `waha_message_resolvable.rb`; não toquei).

### Não verificável daqui

O efeito real das correções na Tozi PROD só é observável depois do deploy: espera-se **issue 68 → 0 eventos** no primeiro tick do cron de 5 min, e **issue 128 → 0 eventos** no primeiro tick horário, com o eval da conta voltando a enfileirar `EpisodeEvalJob`. O spam de notificação para os admins cessa junto — vale avisar o cliente, porque, pelo G1 §4.2, eles vêm recebendo esse push a cada 5 minutos há 20 dias.
